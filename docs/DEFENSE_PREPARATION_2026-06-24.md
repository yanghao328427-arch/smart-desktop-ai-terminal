## 4. 项目亮点

答辩时建议只突出 4 个亮点，避免功能堆砌。

### 亮点一：真实四层物联网闭环

传感器和 RFID 不是装饰，数据真实进入平台；AI 动作也不是只显示在网页，而是下发到 STM32 执行，并由 ACK 证明执行结果。

### 亮点二：身份驱动的个性化 AI

RFID 不仅用于开锁，还会确定当前用户、模式和对话上下文。不同卡片可以进入不同学习或使用场景，用户数据由 SQLite 管理。

### 亮点三：可靠性优先的混合通信

实时事件和 ACK 可优先使用 WebSocket；连接不可用时自动退回 HTTP。STM32 与 ESP32S3 之间始终使用 UART，公网传输变化不会改变底层执行协议。

### 亮点四：不伪造实时状态

系统使用 30 秒新鲜度规则判断设备在线，网页聊天不会把设备错误地标为在线；答辩前还有只读脚本同时检查云端、设备、UART、时间戳和传感器字段。

## 8. 高频答辩问题

### Q1：为什么同时使用 STM32 和 ESP32S3？

STM32负责实时采集和执行，具有稳定的 GPIO、定时器和本地控制能力；ESP32S3负责 Wi-Fi、HTTPS/WSS、RFID 和云端桥接。分工后即使公网链路变化，STM32 的底层硬件协议仍保持稳定。

### Q2：为什么不直接用 ESP32S3 控制全部硬件？

课程要求和工程设计都强调分层。STM32适合确定性的本地控制，ESP32S3适合网络和协议转换；两者分离也更方便定位“云端、网络、串口还是执行器”哪一层出错。

### Q3：AI 是不是固定回复？

不是。云端配置正常时使用 DashScope `qwen-plus` 即时生成回复；后端将完整回复和短播报分离，并根据意图生成硬件动作。云端不可用时会明确降级为本地规则，不会把兜底伪装成云端结果。

### Q4：怎么证明硬件真的执行了？

每个动作都有唯一 action ID。STM32执行后返回相同 ID 的 `BT:ACK`，后端和诊断页记录成功或失败；没有 ACK 就不能宣称完成。

### Q5：怎么避免网页显示旧数据？

后端记录硬件 `last_seen`，超过 30 秒没有新的 heartbeat、telemetry、RFID、ACK 或硬件命令证据，就把设备和 UART 标记为离线。

### Q6：RFID 有什么实际意义？

RFID 是用户身份和上下文入口，不只是开锁。卡片绑定用户和模式，刷卡后切换 OLED 页面、权限和 AI 对话上下文。

### Q7：数据库保存什么？

SQLite 保存用户、卡片、用户会话、对话事件、用户摘要、RFID 注册请求和审计事件。密钥不写入数据库。

### Q8：WebSocket 断开怎么办？

ESP32S3 会恢复 HTTP 命令轮询，按钮和 ACK 也退回对应 HTTP 接口；UART 底层链路不受影响。

### Q9：为什么语音使用电脑麦克风？

ESP32S3 板载麦克风在大包上传和稳定 ASR 上没有达到答辩可靠性要求，因此当前采用实体 KEY2 触发电脑麦克风 PTT。它仍是真实语音输入，只是采音设备放在答辩电脑上。

### Q10：华为云在系统中是什么角色？

当前答辩主链使用 Hugging Face 部署后端。华为云 IoTDA 是可选的并行设备云扩展，CCI 是未来可迁移的容器平台，不把未启用部分包装成当前主链。

### Q11：系统最大的工程难点是什么？

不是单个模块，而是跨层一致性：语音或文本经过 AI 后生成动作，动作跨公网、Wi-Fi、UART 到达 STM32，再通过 ACK 回到页面；同时还要避免旧状态、重复刷卡和网络断线造成误判。

### Q12：还有哪些不足？

STM32 Flash 空间紧张；免费 Space 有冷启动和限流；最新 WSS 主路径还需实机验收；长期历史数据和正式用户权限仍属于产品化扩展。

5. 展示识别文本、AI 回复、SYN6288 播报和 ACK。

### P3：现场降级

- Hugging Face 限流：停止反复刷新，等待后重跑 readiness；先讲架构和本地硬件。
- 云模型不可用：明确说明降级状态，展示本地规则和硬件闭环，但不要称为云端 AI。
- 语音不稳定：切换到 Web 文本输入，保住 AI → 动作 → ACK 主线。
- RFID 不稳定：使用已注册卡重试；模拟 UID 只能标为调试入口。
- WebSocket 不稳定：保留 HTTP relay 兜底，不在现场临时改网络。
- 小程序异常：使用 Web 控制台；两者本质上读取同一后端。
